Say this cold

What is this system?

An AI-powered route advisory system for Nairobi's matatu network. It combines a graph model of the real GTFS transit data with a conversational agent, so a commuter can either browse a map or just ask a question in plain language.

What's the map for, versus the chat?

The map is how you see the network — the chat is how you ask about it. Same data, same graph analysis underneath, two ways in. The map plots all 4,284 stops, shows a suggested route as text when you pick two stops, and can highlight coverage gaps in colour. The chat does the same three jobs conversationally, for someone who'd rather type a question than click two dropdowns.

Who are the primary users?

Two roles, not three. A Commuter — signed in or anonymous — uses the map, planner, and chat freely. An Administrator additionally sees usage reports and the most-searched-routes table. No separate "planner/researcher" role, because it would read the exact same reports an admin already can — no distinct permission to justify it.

How a request actually flows
1
Ingest the GTFS feed Digital Matatus dataset (stops, routes, trips, stop_times, shapes) parsed and loaded into PostgreSQL on startup. GtfsIngestionService
2
Build the graph, in memory A directed weighted multigraph — one node per stop, one edge per consecutive stop-to-stop hop on a trip — built once at startup with JGraphT. MatatuGraphBuilder
3
Analyse it A custom Dijkstra whose search state is (stop, route you arrived on) — so a transfer penalty applies exactly when the route changes — plus Kosaraju's algorithm for strongly-connected-component coverage gaps. RoutingService · CoverageAnalysisService
4
Expose it two ways Direct REST endpoints for the map (deterministic, fast, no LLM involved) — and the same routing/coverage logic wrapped as tools a Spring AI agent can call when someone asks in natural language. RouteController · CoverageController · RouteAdvisoryTools
5
Ground the agent beyond the graph A RAG pipeline — Ollama embeds a small local knowledge base into pgvector — lets the agent answer about things the 2019 GTFS data can't know, like the December 2024 CBD route gazette. KnowledgeBaseIngestionService
6
Render it Next.js talks to the backend through a same-origin rewrite proxy — no CORS config needed anywhere — with Leaflet for the map and a chat panel for the agent. next.config.ts rewrites
Roles & access
COMMUTER

Default role on sign-up. Full access to map, planner, chat — and, once signed in, a personal journey history. No account is required for any of this.

ADMIN

Everything a commuter has, plus /api/reports — usage stats and the most-searched-routes table. Seeded at startup; sign-up can never grant it.

Session cookie, not a JWT — the browser only ever talks to the app itself through the proxy, so there's no third-party client to justify token issuing/refresh. CSRF stays on regardless, via a double-submit cookie.

Your best "I actually debugged this" story

Same stop name, two different stops, opposite results.

Nairobi's feed has several stops sharing one name. The agent once resolved "Limuru Terminus" to the wrong one and told a user no route existed — when one plainly did.

Ngara → Limuru Terminus  [0110IRT → 0113LMD]  100%
Ngara → Limuru Terminus  [0110IRT → 0110ILU]  0%

Fix: route resolution now evaluates every served candidate pair for a name, not one guess — and the most-searched-routes report groups by stop ID, not name, so this exact ambiguity shows up as data instead of staying hidden.

If asked what's missing — say this, not nothing

Swahili interface

Promised in the proposal, not yet implemented — it's a system-prompt change, scheduled before submission.

Walking-distance coverage

Implemented graph-theoretic coverage (Kosaraju SCC + degree) instead. Geographic analysis is future work — PostGIS is installed and ready for it.

Route line drawn on the map

/api/routes/suggest returns stop names only, no coordinates. A route shows as text plus highlighted origin/destination markers — drawing the line needs a new endpoint over the GTFS shapes data.

Admin route editing

Roles and reporting are built and tested; editing route data is the next increment.

Transfer penalty tuning

Was 5 minutes — too cheap, so routing over-transferred. Raised to 15 minutes to match what a real commuter actually trades off.

Likely questions, ready answers

Why Claude and not a local model for the chat?

Tool-calling reliability. The routing and coverage logic is deterministic and runs locally either way — only the language layer is remote, and it has to reliably call suggestRouteBetweenPlaces and getCoverageGapSummary rather than hallucinate an answer.

Why a multigraph, and why directed?

Directed because a matatu doesn't always return by the same road. Multigraph because two different routes can connect the same pair of stops, and collapsing that into one edge would hide a commuter's actual choice.

Why Kosaraju's algorithm specifically?

It finds strongly-connected components on a directed graph. A stop can have service arriving with none leaving (or vice-versa) — weak connectivity would hide that asymmetric-service problem entirely.

No CORS config anywhere — why not?

The browser only ever calls relative /api/* paths. Next.js rewrites proxy those to Spring Boot server-side, so from the browser's point of view every request is same-origin.

What would you build next, given more time?

In order: Swahili in the system prompt, the route-geometry endpoint so the map can draw an actual line, then admin route editing.
